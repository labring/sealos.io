Eaglercraft hosting becomes easier to plan when each address and process has one clear job. A player opens a **Browser Play Link** in a browser or enters a **WebSocket Server Address** in an existing compatible client. The **Eaglercraft Gateway** carries that session to the **Game Server**, which owns the world and saves it to a **Persistent World**. The **Server Management Panel** gives the operator a separate place to check readiness, players, storage, and commands.

This article explains the architecture with the Sealos template as the first concrete example, then maps the same design to a **Self-Hosted Eaglercraft Deployment** on an Ubuntu VPS or through Docker Compose. It gives you enough context to choose a path and find the right operational guide.

## The Architecture in One View

The request path has four core stages:

```mermaid
flowchart LR
    B[Browser Client] -->|HTTPS page or WSS session| G[Eaglercraft Gateway]
    G -->|game protocol connection| S[Game Server]
    S -->|world and player data| W[Persistent World]
    P[Server Management Panel] -->|local management requests| S
```

The diagram's text alternative is: a Browser Client opens the Client Website or starts a WSS session; the Eaglercraft Gateway accepts the session and forwards it to the Game Server; the Game Server reads and writes the Persistent World; the Server Management Panel sends operator commands to the Game Server. Each box can run in one Runtime Bundle while retaining a separate operational role.

The browser experience has two layers. The Client Website serves the JavaScript and assets that make the game playable in a browser. The Eaglercraft Gateway accepts the browser's WebSocket upgrade and translates that public connection into the runtime's game connection. A player may use the supplied Client Website or an existing compatible client that connects straight to the Gateway.

## What Each Component Does

| Component               | Job                                                                        | Typical operator or player action                           |
| ----------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Browser Client          | Runs the game interface and accepts keyboard, mouse, and sound input.      | Open the Browser Play Link and select Multiplayer.          |
| Client Website          | Serves the browser client page and its static assets.                      | Share its HTTPS URL with players.                           |
| Eaglercraft Gateway     | Terminates Eaglercraft WebSocket connections and forwards player sessions. | Publish it through HTTPS and WSS.                           |
| Game Server             | Applies game rules, tracks players, and owns the multiplayer world.        | Wait for Paper readiness and save the world.                |
| Persistent World        | Stores world, player, plugin, and server data on durable storage.          | Keep the volume or bind mount during restarts and recovery. |
| Server Management Panel | Exposes readiness, player, world, plugin, and command controls.            | Open the owner-only `/admin` path.                          |

The player needs a compatible client. The host needs the Gateway, Game Server, and storage. A Runtime Bundle can package all of them, which is why the Sealos path feels like one application even though the connection crosses several responsibilities.

## HTTPS, WSS, and the Three Addresses

The same public hostname can expose several paths, while each URL has a distinct purpose.

| Address                  | Protocol and example                    | Enter it or open it here                                   |
| ------------------------ | --------------------------------------- | ---------------------------------------------------------- |
| Browser Play Link        | HTTPS, `https://play.example.com/`      | Browser address bar.                                       |
| WebSocket Server Address | WSS, `wss://play.example.com/`          | Multiplayer server field in an existing compatible client. |
| Server Management Panel  | HTTPS, `https://play.example.com/admin` | Operator browser after the application is ready.           |

HTTPS provides the page and management interface. WSS is the encrypted WebSocket transport used by a compatible client. A browser address bar expects the Browser Play Link; a client's Multiplayer form expects the WebSocket Server Address. The `/admin` path belongs to the operator workflow and should stay protected by the panel's credentials and the deployment's access controls.

The public addresses terminate at the Gateway. The private Game Server listener can remain on the local machine or container network. That split lets the Gateway handle the browser protocol while the Game Server stays behind the public entry point. The management panel can also bind to loopback, as in the Ubuntu VPS and Docker Compose guides, and reach the operator through an SSH tunnel when the deployment requires it.

## Choose a Hosting Path

| Path                                                | Best fit                                                                    | What you operate                                                                       |
| --------------------------------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Sealos template                                     | You want the Runtime Bundle and a managed application surface.              | Resource allocation, credentials, Persistent World, and recovery copies.               |
| Self-Hosted Eaglercraft Deployment on an Ubuntu VPS | You administer the host and want direct control of services and Caddy.      | Runtime files, systemd services, firewall, TLS entry point, panel access, and backups. |
| Docker Compose                                      | You already operate a Docker host and prefer a reproducible data directory. | Compose files, image updates, bind-mounted data, Caddy, and backup and restore checks. |
| Shared World                                        | You need a temporary session from a compatible client's sharing feature.    | The host browser session and that client's sharing setup.                              |

The Shared World path keeps the world's lifetime tied to the sharing session. A hosted Game Server keeps the world available while the application and its resources remain active. A VPS or Compose host gives you direct control over the public entry point and stored files. The Sealos template compresses the setup work into a deployable application while keeping the same component model.

## Use Your Own Domain

An owned domain gives players a stable name such as `play.example.com`. The configuration shape has three parts:

1. Create a DNS record that points the name at the public host or load balancer.
2. Let Caddy obtain and renew the certificate for the name.
3. Reverse proxy HTTPS and WebSocket traffic to the Eaglercraft Gateway while the Game Server stays on its private listener.

This minimal Caddy example shows the public routing shape for a self-hosted runtime:

```text
play.example.com {
    reverse_proxy 127.0.0.1:5200
}
```

Caddy forwards WebSocket upgrades through `reverse_proxy`, so the same site block serves the Client Website and the WSS connection. Keep the management panel on its local listener when that matches your security plan, then reach it with the documented SSH tunnel. The exact host port, container name, and TLS environment depend on the deployment path.

## Direct Paper and Proxy-Based Integration

The simplest stack puts the Eaglercraft Gateway directly in front of one compatible Paper Game Server. This is the model used by the Sealos template and the self-hosted Runtime Bundle.

| Integration shape        | Connection flow                                                           | Choose it when                                                      |
| ------------------------ | ------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Direct Paper integration | Client → Eaglercraft Gateway → one Paper Game Server.                     | One Eaglercraft world owns the public entry point.                  |
| Proxy-based integration  | Client → Eaglercraft Gateway → proxy layer → one or more backend servers. | You already operate a proxy and need its routing or identity model. |
| Shared World             | Player browser → shared client session.                                   | You need a short-lived session with minimal administration.         |

Proxy-based designs add routing, compatibility, identity, and failure boundaries. Keep the Gateway's WebSocket behavior, the proxy's forwarding mode, the backend version, and player identity handling aligned. Capacity, plugin compatibility, and cross-server movement belong in a dedicated integration review. The [existing-Java-server integration guide](/blog/eaglercraft-existing-java-server/) is the planned destination for that detailed path.

## Common Address Mistakes

| Symptom                                         | Correct check                                                                                                                   |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| The browser says the server address is invalid. | Open the HTTPS Browser Play Link in the address bar.                                                                            |
| Add Server rejects the value.                   | Paste the `wss://` WebSocket Server Address into a compatible client's Multiplayer field.                                       |
| The panel opens while joining fails.            | Wait for Paper readiness and inspect the application logs or Game Server status.                                                |
| A friend reaches a different world.             | Compare the hostname and server entry, then confirm both clients use the intended Game Server.                                  |
| A restart loses progress.                       | Confirm the original Persistent World volume or bind mount stayed attached and complete a recovery check separately.            |
| The public page does not open.                  | Follow the [troubleshooting guide](/docs/guides/app-deploy/troubleshoot/) after checking the application status and public URL. |

The address table is the fastest diagnostic: HTTPS means a browser page, WSS means a game connection, and `/admin` means operator access. Credentials also have separate roles. The Administrator Password controls the panel, while Player Account passwords control in-game authentication.
